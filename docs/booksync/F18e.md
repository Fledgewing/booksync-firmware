# F18e: lifecycle reading progress

BookSync ports the companion's progress I/O from
`server/bookorbit/BookOrbitServerAdapter.kt:242–264` on the integration repo's
`origin/feature/0.12`. Only `server/bookorbit/LifecycleProgress.*` owns the
protocol, wire values and pending-reply codec. The concrete route selector uses
GET `/koreader/syncs/progress/<document>` for fetch and PUT
`/koreader/syncs/progress` for delivery. The transport uses the F15 sync login,
never an App-Attest route. It sends the original percentage, raw protocol locator,
capture timestamp and durable device identity. Missing remote progress (GET 404),
an absent percentage and an explicit zero are separate values. Remote timestamp,
label, web and reset metadata survive the checkpoint without policy interpretation.

F19 owns ahead/behind/override/consent and whether a capture may be sent. A durable
explicit `deliver` intent enters the private evidence seam; its default is fetch.
No percentage comparison or reader navigation exists in this phase. F08 source
identity and raw native checkpoint bytes remain unchanged, including unknown and
binary bytes. Evidence must supply an existing lossless protocol locator; this
slice does not translate a native EPUB anchor to a KOReader locator. Unsupported
mapping stays queued. The production adapter remains offline, consistent with
F18a–d; live transport/evidence wiring and outgoing activation are not enabled here.

F17 is the only writer and supplies the borrowed token. F18a–d must already be
acknowledged. F15 readiness, connector identity, account scope, epoch and the
exact source revision gate transport and local publication. Incompatible editions
remain unresolved, rather than transferring a locator across editions. Account
changes after a remote operation leave an uncertain attempt. Acquisition-only
credentials cannot deliver or publish progress.

A successful request returns an incomplete `BSP1` checkpoint containing the full
remote result and unchanged match/stats checkpoint. F17 persists it before the
next call publishes it to an account/source-scoped durable progress projection.
Publication never changes native reader state. The evidence provider must recheck
scope/source and make publication idempotent: a cut after publication but before
ack repeats publication without repeating transport. A failed publication retains
the pending reply. Final acknowledgement restores the preceding checkpoint; only
then can F17 finish the lifecycle entry. GET 404 also publishes absence durably.

Unknown PUT results require reconciliation, never a blind resend. The transport
must recover the original outcome or prove noncommit before resending unchanged
capture. A matching GET value alone is not proof of the original commit, and a
newer remote value must never be overwritten to settle an old attempt. If proof
is unavailable, keep the attempt uncertain. The fake server has a separate durable
receipt; this does not assert that a production reconciliation endpoint exists.

## Bounds and checks

No heap allocation, task, native reader change, new screen or persistent global is
introduced. Borrowed views and small fixed values use the task stack; the worker
owns output scratch. The GET route uses 57 stack bytes. Protocol position is
bounded to 4096 bytes and label to 100, matching the companion. The complete reply
and original checkpoint must also fit the existing 1024-byte journal checkpoint.
Larger results stay uncertain without truncation or acknowledgement. This is an
explicit capacity refusal, pending a streamed/larger adapter checkpoint design.
Journal envelope and EPUB cache formats do not change. `BSP1` is a new private tag,
documented in `docs/file-formats.md`; no existing checkpoint layout changes.

Fourteen host cases compile production progress, route selection, F15 accounts,
F17 owner and real publication/journal code. They cover GET/PUT selection, zero
versus absence, raw native/stats preservation, source/account/epoch isolation,
invalid/oversized replies, failed local publication, unavailable commit proof,
remote crash/timeout before and after commit and every storage operation with
eager and delayed persistence.

The three simulator profiles each run a durable fake-server progress suite with
independent remote and projection receipts, real HAL storage and abrupt process
exits around remote commit, projection publication and owner checkpoints. These
are scripted restarts, not retries of a failed scenario. ESP32 internal heap,
largest-block and stack watermarks cannot be represented by the native HAL;
reports retain explicit unavailable values and a zero progress-allocation count.
All hardware builds force-link this otherwise dormant handler for the reserve gate.

Maintainer hardware verification after live activation is authorized: on X4 Pro,
X4 Classic and X3/C3 X4, fetch and deliver a synthetic book position, interrupt
around commit/publication, restart and verify one remote effect and durable
reconciliation. An uncertain write with no proof must remain pending; a newer
remote position must survive. Read/turn/close/reopen at the native anchor must
remain unchanged, with no unsolicited navigation or consent UI from this phase.
Inspect internal heap/largest block and worker stack watermarks. No EPUB cache
reset is required. Agents do not access devices or serial ports.
