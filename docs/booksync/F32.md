# F32 update admission and return recovery

This slice implements the serial policy/port seam in `system/Update.*` and
`Diagnostics.*`. It has no live feed, downloader, hardware flash writer, automatic
restart, Library update route or renderer. Test ports simulate writing/selecting
an image and booting either slot. The complete dormant policy graph remains in
hardware images and is required by the map/size guard.

Installation reuses F31 eligibility/version ordering and F30 staged size, SHA-256,
root, certificate and artifact-signature verification. Unlike F30's rollout helper,
F32 requires a verified signature to install. Board and exact partition-map digest
must match the device; the port must validate every ESP image segment/checksum and
lock the verified bytes until write/selectBoot finishes. Partial images or images larger than the actual inactive-partition capacity
fail before writing. The existing CI budget remains the sole 128 KiB reserve
authority. This does not change partitions or trust inputs.

The future production port must supply fresh main-loop state from F11 admission
(network drained, framebuffer restored), F12 reading/presentation state, and F29
activation readiness/recovery. Install and restart require visible Home, no reading
(including in-book panels), no sleep, no activation recovery and no network/display
owner. The synchronous port cannot dispatch UI/events, admit a reader, perform
network work or reboot. Only this serial owner may change update receipts/slots.
The restart callback runs separately after another fresh admission check. Back
and Cancel cannot interrupt a started write. No permission survives a deferred call.

Q5 return checks lock the available previous image, verify board/map/completeness
and signed trust (including existing validated A/B boot rollback), and obtain a positive compatibility proof tied to that exact digest and
the **current** durable records/schemas, including retained activation. Version
age or a previous successful boot alone proves nothing. A future port must refuse
unknown schemas and unproven versions; this slice enables no real return target.
An earlier offer cannot authorize a later return: admission and compatibility are
checked again. Local receipts never claim that a return reverses remote writes.

The BSU1 receipt commits source/target digests before any boot-slot change. On the
next boot, only the actual verified boot image can prove completion, return or
interruption. An unknown image or damaged current receipt remains unknown; an old
backup success never substitutes for it. Failed/uncertain writes retain intent.
No diagnostic operation uploads, displays, modifies native reader files or handles
account data. This one update receipt is separate from F43's five crash reports.

## Presentation mapping

No screen is implemented in this service slice. Future Library-only B3 presentation
uses the existing approved `SCREENS.md`/`mockups.html` states: `update-deferred`,
`update-confirm`, `update-install`, `update-restart`, `update-board`, `update-layout`,
`update-signature`, `update-root`, `update-interrupted`, `update-rollback`,
`update-no-rollback`, `update-rollback-progress` and `update-success`.
Recovery wording must wait for `recover()` proof. No additional state or keyboard
is introduced. B5 crash/export/reset presentation remains F43's separate scope.

## Verification

Host tests compile production policy, signature verification and SD publication.
They cover device/map/hash/length/trust rejection, quietness, activation and display
ownership, unknown boot, changed compatibility proof, failed writer, stale success,
and every publication operation cut with both delayed and eager metadata durability.
All three native simulator profiles run the shared 22-check fake install → source
boot recovery → target boot completion → compatible return scenario, using isolated
synthetic SD. They exercise production receipt publication and boot digest matching,
with zero presentation callbacks. Simulator memory is not hardware acceptance:
policy uses no heap or new task; receipt encoding/decoding uses 76-byte local arrays
and image metadata uses fixed-size structs. FilePublish retains its existing HAL
file-handle lifetime. Transient nested frames require hardware stack-watermark checks.

Maintainer hardware verification after a real port is separately reviewed: on X4
Pro, Classic and C3, keep an EPUB open and attempt a staged update/return; expect
no flash write, display parking or restart. Return Home and test signed wrong-board,
wrong-map, truncated and corrupted images; expect refusal with the current image
unchanged. A complete valid image may install only after activation recovery and
network/display ownership clear. Interrupt each receipt/write/boot-selection stage;
confirm next-boot diagnostics report only the actual image. Offer return only when
that version has explicit current durable-state compatibility evidence. Measure
internal heap/largest block and task stack watermark; on S3 also inspect PSRAM.
No EPUB cache reset is needed. This task performs no device or serial operation.
