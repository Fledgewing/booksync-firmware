# F26c: legacy Tailnet identity retention

BookSync imports this state **in place**. F10 deliberately kept the same NVS
namespace, key spelling, type, MicroLink pin and default device-name algorithm.
Copying identity into a second namespace would add an unnecessary failure point.
The worker-only `import/Identity.*` audit returns version-1 evidence; it does not
install it, start Tailnet, pair, activate a sync writer or change boot routing.
F29 owns cutover and durable recovery proofs.

## Source contract

- `tailnet/shim/Tailnet.cpp:50` and `:113` define the shim's namespace and keys.
  The eight flags/route/login entries retain their existing types and values.
- Pinned MicroLink `components/microlink/src/microlink.c:34` defines the six
  identity blobs. All six must exist with blob type and exactly 32 bytes before
  the audit reports `RetainedInPlace`. No public key is calculated from a private
  key; no mathematical key-pair validity or live pairing claim is made.
- F03 `test/fixtures/legacy/nvs/entries.json` and `optional-keys.json` are the
  logical NVS source fixtures. The WireGuard timestamp floor, optional control
  cache, peer table and runtime config remain in their existing namespaces.
  Cache/config payloads and login presentation are retained opaquely, not parsed
  or copied. Unknown entries/types, unknown relay enums, partial identity and
  read failures produce unresolved statuses and leave the source unchanged.
- Old stores missing optional fields retain their complete identity. An empty
  store reports `Absent`, never permission to generate one. A joined flag without
  the six blobs reports `Incomplete`. Unresolved results have no fingerprint.

The private SHA-256 fingerprint covers only the six opaque identity blobs in
canonical order, independent of NVS enumeration order. It is not a whole-NVS
backup, pairing assertion or cutover authorization. It must never be presented
or logged. F29 must rerun the audit with Tailnet stopped and serialize namespace
ownership; a prior audit is not evidence against intervening NVS changes.

## F29 pre-initialization prerequisite

The current Arduino core's `cores/esp32/esp32-hal-misc.c:331-337`
(`framework-arduinoespressif32`) calls `nvs_flash_init()` before application
setup. On `ESP_ERR_NVS_NO_FREE_PAGES` or `ESP_ERR_NVS_NEW_VERSION_FOUND`, its
fallback calls `esp_partition_erase_range(partition, 0, partition->size)` and
initializes NVS again. An application-level audit cannot preserve bytes already
erased by that fallback. F29 must guard this **before Arduino initialization**
and preserve unsupported/unreadable physical NVS without formatting it. Merely
checking this audit before starting Tailnet is insufficient for that case.

Separately, pinned MicroLink `microlink.c:57-118` generates replacement or
ephemeral keys when its private-key read or namespace open fails. F29 must never
invoke that loader for unresolved legacy identity. An `Absent` result alone is
not permission to generate keys or discard an unreadable partition.

A successful preflight also cannot authorize the loader's generation fallback
if a later NVS read fails. Cutover needs a strict reuse-only transport path for
legacy identity: failures between audit and actual key loading must return
unavailable without writing or generating keys. F29 must test those cuts as well
as the pre-initialization partition failures; a one-shot preflight is insufficient.

F03 contains typed logical NVS exports, not raw flash images. This slice's
unknown/corrupt tests prove read-only record retention and failure handling after
NVS is available; they do not qualify the framework's pre-setup recovery path.
Neither framework startup nor activation is changed here. Guarding the destructive
fallback and testing raw partition initialization errors remain mandatory F29
cutover work; no upgrade activation or physical-flash retention claim is made by
this dormant audit.

## Bounds and dependency rationale

No application heap allocation, persistent duplicate, filesystem write, NVS
write/erase/commit, transport call or random/key-generation API exists in the
importer. It uses a 32-byte scoped key buffer and a streaming SHA state (compile
bounded to 256 bytes), both explicitly wiped on all exits. NVS's own iterator
allocation is bounded to one live iterator; it is released on success and every
fault. Inventory stops after 64 entries per namespace and reports unsupported.
Handles close on every path. Error logs contain fixed text only.

The source-role inventory classifies both files as import. The boundary guard
permits the exact `mbedtls/sha256.h` digest primitive while continuing to reject
TLS sessions, HTTP, Wi-Fi, transport, adapter and Tailnet includes. Rejection
fixtures cover both TLS implementations; the digest include confers no transport
capability. The dormant full-link root is required by the hardware size gate,
so garbage collection cannot hide the import's image cost before F29.

## Verification

Tests were written before implementation and failed on the absent importer.
`python3 test/host/import_identity/run.py` compiles the production NVS code against
fake read-only NVS populated from F03. No mutation or key-generation API is
provided by the fake. It executes two independent boot processes, testing exact source retention across the full
F03 corpus, canonical fingerprints, one changed blob, every missing/mistyped/
short key, missing old optional fields, unsupported future entries/enums,
oversized inventory, timestamp type, and all 58 read/open/iterator fault cuts.
F10's separate test executes the pinned key loader twice and requires zero writes
and random calls with all 192 original identity bytes unchanged.

`test/simulator/identity_import.py` runs this production-code/fake-NVS scenario
once per profile as part of `boot.py`. These are native fault-model scenarios,
not a real NVS partition or radio. The full simulator harness also preserves
native reader behavior. Simulator heap and stack cannot qualify ESP32 memory;
scenario receipts leave internal heap/largest-block/high-water metrics unknown.

Maintainer hardware acceptance, after F29 integration: on X4 Pro, X4 Classic and
C3 X3/X4, upgrade a synthetically provisioned paired test reader, boot twice,
reconnect without re-pairing and verify route/name lookup and the same Tailnet
node/pairing. Test an incomplete/unsupported NVS image remains unresolved without
regeneration. Open/read/close/resume a local book through connection loss, with
no unsolicited navigation or reader changes. Inspect internal largest-block and
worker stack watermarks. No EPUB cache reset is needed. No device or serial port
was accessed for this slice.
