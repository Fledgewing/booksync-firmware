# F30: signed update trust port

BookSync's existing X4 update contract is ported without connecting a feed,
starting a task, installing an image, or changing reader behavior. No B3 screen
is implemented. F31 owns version/channel/bridge selection and packaging; F32
owns install admission, board/map validation and return/recovery.

## Source contract

The source inputs are the BookSync integration repository's
`xteink/orbify/core/UpdateSignature.{h,cpp}` and `Ed25519Verify.{h,cpp}`,
`xteink/orbify/OtaManifest.h`, and signed-OTA/redirect patches 0050/0055.
The streaming list parser derives from CrossInk's release parser plus BookSync's
list/signature/identity changes. The GPL notices and existing repository licenses
are retained; the Ed25519 field/group arithmetic is public-domain TweetNaCl.

The `xteink.yml` workflow builds `xteink/releases.json` on the `xteink-feed`
branch, carries each asset's `orbify_signature`, and signs the feed with tag
`xteink-feed` and asset `releases.json`. These immutable signing domains and the
legacy field name stay unchanged. A certificate is 4-byte big-endian serial,
32-byte release public key and 64-byte root signature; the artifact adds another
64-byte signature. The root signs `orbify-release-key-v1\n` plus serial/key;
the release key signs `orbify-artifact-v1\n<tag>\n<asset>\n<sha256>\n`.
Repository renames therefore do not invalidate signatures.

The production public root, minimum serial (1), and rollout enforcement (false)
are copied unchanged from BookSync's `shared/release-signing.json`.
Test roots are exclusively existing public throwaway-key fixtures, separate from
the production trust inputs. No signing functionality or private keys are included.
F31 must preserve these inputs when integrating release packaging.

## Caller contract

`Feed` streams single-release objects or release lists into fixed storage and a
function-pointer visitor. Visitors are provisional: no candidate may be acted on
until HTTP success, `complete()`, and detached-feed trust under the configured
enforcement policy. Input order is not version order: retained bridges may
precede newer product heads. Ignore redirect/error bodies with
`feedResponse`; HTTPS/redirect transport admission remains the transport's job.
On retry, reset both the parser and the caller's selected candidate. A successful
empty list is an empty result, never permission to reuse a cached candidate or
fall back to another origin. The workflow has no firmware withdrawal-list wire
format: withdrawing/removing an entry makes it absent from the next feed.
No Android withdrawal protocol is invented here.

The parser retains product identity and prerelease/draft flags for F31, filters
draft visitor entries, resets signatures/identity per release and attempt, and
rejects incomplete responses, trailing documents, truncated signed fields and
negative/overflowing sizes. Unknown metadata remains ignorable.

`checkDownload` preserves the existing certificate/root/serial checks and binds
the signed URL basename to the expected device stem. `checkStaged` takes the
SHA-256 computed from the actual staged bytes, checks it against the manifest and
checks the staged length before signature policy. Hash/length failures always
reject. Signature failures reject under enforcement; the existing rollout policy
otherwise logs and allows them. The caller owns those logs via `describe()`.
`decodeDetached` and `checkFeed` decode and verify the workflow's detached
signature format and exact feed identity. The caller must hash the complete raw
feed bytes and never substitute a parsed/re-serialized feed digest.

There are no URLs/default/fallback origins or HTTP/OTA APIs in production F30.
Library/UI boundaries and the sole sync writer are unchanged.

## Resource and verification notes

The parser is caller-owned fixed storage, not a resident singleton or stack local
in a new worker. Integration should allocate it once for the update job lifetime.
Ed25519 allocates a fallible 1920-byte owned work area during cold verification;
stack storage would consume too much of the C3 task stack, while permanent static
storage would occupy RAM during reading and prevent safe independent callers.
It frees the area before returning. Certificate and artifact verification run
sequentially. The inherited 256-byte signing-message buffer and 65-byte digest
normalization buffer bound stack use independently of feed/image size; no image
or whole feed is buffered. Firmware uses the existing mbedTLS SHA-512 API; host
and simulator retain the source's portable known-answer-tested implementation.
A retained, uncalled linker entry keeps parsing and crypto in all measured images;
the GNU hardware builds additionally name that entry with `--undefined`. Its
explicit, fallible parser construction keeps the complete callback graph linked
without consuming static RAM or a large task-stack local. The entry is never run.

`test/host/update_verify` ports the existing public signature/OTA fixtures, RFC
8032 and SHA-512 known answers, then adds staging/reset/withdrawal, malformed
input and detached-format checks. `test/simulator/update.py` runs a fake feed in
all three profiles, hashes actual corrupt synthetic app bytes, refuses both that
app and a feed digest changed to match it, and checks wrong-device/root/serial,
redirect/chunk/reset/empty-feed behavior. It performs no network or flash action.
The shared fixture feed intentionally uses illustrative sizes; positive staging
checks use its supplied digest/size, while corrupt-byte tests compute a real hash.

The simulator reports parser/release sizes. Its native heap/stack figures are
not hardware acceptance, and F30 creates no task to measure a high-water mark.
Hardware acceptance belongs to the maintainer after F32: on each reader, offer a
signed synthetic update, a corrupt stage, a relabeled other-board asset and an
empty/withdrawn feed; expect rejection before erase/install, unchanged reading
position, and no unsolicited restart. Inspect internal free/largest heap and the
update worker stack high-water during both certificate and artifact verification.
No EPUB cache reset is needed. No device or serial port was used for F30.
