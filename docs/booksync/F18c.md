# F18c: annotation lifecycle

BookSync ports the companion's annotations phase from `BookOrbitSync.kt`
(`phase` annotations branch and `applyRemote`), at integration commit
`7b3220fe6920180ffbbc34b9307508db71b6c893`. This independently implemented
firmware phase covers highlights, attached notes, bookmarks and tombstones.
No new screen, native reader behavior or outgoing activation is introduced.
The concrete adapter remains offline until import/activation proof is complete.

`LifecycleAnnotations` runs only with F17's borrowed writer token. F18a's BSM1
checkpoint supplies the matched source and digest and remains byte-for-byte intact
for later phases. Incompatible editions skip annotation exchange. F15 sync
readiness, connector identity, capability and current account epoch gate every
request and application. An account change during delivery cannot acknowledge it.

The adapter-private workspace is an injected durable persistence boundary, like
F18a's captured evidence and injected transport. Its contract freezes outgoing
rows before sending, scopes every record by adapter/account/entry/source, stages
the complete remote reply before local application, and atomically advances each
kind's cursor only after acknowledgement. Its native application transaction must
recheck that the file is closed, preserve unrelated fields and persist verification
records before producing receipts. A damaged or unavailable workspace fails closed.
Production SD capture/application wiring remains behind the later import/activation
gate; host and simulator fixtures supply synthetic durable workspaces through
FilePublish. These fixtures are not a native sidecar importer or live HTTP client.

Highlights/notes and bookmarks exchange separately, at most 16 changes each per
owner step. More batches retain the phase attempt; a bounded later step resumes
without acknowledging the phase early. Uncertain exchanges repeat the same frozen
batch using the protocol's datetime/location deduplication. Pending remote replies
survive separately from the F17 journal and are applied and acknowledged before
another exchange for that kind. A lost acknowledgement repeats application and ack
idempotently, including deletion of an already absent record. No HTTP idempotency
field or invented remote acknowledgement is used.

Complete keys establish absence only for a known, current native capture of a
closed, present book. Historical snapshots and open books never establish deletion.
The full key list accompanies only the first batch; the completeness flag follows
the companion's subsequent-batch behavior. Disabled sync finishes already staged
remote applications after close but starts no new exchanges. Fully completed
closed-file exchanges mark the native state known. Missing/open files retain
pending work without applying it.

Identity matching uses server ID, datetime plus raw locator, or protocol key.
The merge helper preserves existing passage text when the response omits or empties
it, clears absent notes, uses bookmark titles and removes bookmark drawers.
New non-xpointer highlights fail application; existing ones can be updated.
Highlights remain pending verification and receipts use verified=false until the
native anchor verification workflow confirms them. Pending-verification rows cannot
be reuploaded. The workspace supplies explicit applied/failed receipts, preventing
an application failure from becoming a successful remote acknowledgment.

The handler allocates no heap, task, framebuffer or annotation payload array.
Records and decoded replies borrow caller-owned bounded storage. Server replies
and receipts larger than 16 rows stream through a reusable record, including up
to 100 pushed additions and 500 bookmark tombstones; no full reply array is required. String bounds
match the companion's captured-field limits; keys are capped at 1024 with overflow
rejected, never truncated into a complete-key deletion claim. The small metadata
views together exceed 256 stack bytes but avoid copying payloads that can be tens
of kilobytes. Hardware reserve measurements retain the dormant phase through its
link anchor. Native host heap/stack metrics cannot qualify embedded runtime fit.
There is no journal, EPUB cache, partition or native-save format change.

## Verification

Host tests compile the production phase with Account/Auth, F17 SyncOwner,
LifecycleJournal and FilePublish. Fault cases include before/after commit crash
and timeout, all workspace/journal publication cuts with eager and delayed metadata,
staged reply restart, lost ack, stage/application/advance failures, account/source
isolation, disabled sync, open-file deferral, bounded batches, deletion receipts,
merge behavior and pending verification exclusion.

Each simulator profile runs `test/simulator/lifecycle_annotations.py`: 13 scenarios,
8 abrupt exits and 40 boots. The fake server, workspace, synthetic local annotations
and F17 journal persist independently. Add/edit/delete replay leaves exactly the
same two live records and one tombstone outcome, with one commit per kind.
The phase advances through F17 only after both kinds finish; state stays unavailable.
The required profile boot gate includes this suite alongside retained reader tests.

Maintainer hardware verification after activation: on X4 Pro, X4 Classic and
X3/C3 X4, use a synthetic matched EPUB with highlights, notes and bookmarks.
Close the book before applying remote add/edit/delete, restart on both sides of
exchange and acknowledgement, and confirm no duplicate or resurrected rows. Keep
the book open to confirm local saves continue and remote application waits. Disable
sync with pending remote work and confirm that work completes after close without
starting a new exchange. Historical captures must not delete newer notes. Check
native anchors, highlight verification and read/turn/close/reopen behavior, plus
internal free heap, largest block and sync-worker stack high-water. No EPUB cache
reset is required. No device or serial port was accessed by this slice.
