# F35a — Home add/remove/reset

The editor uses only Library values/intents. `editLayout()` accepts one pending
revision-checked operation; acceptance does not mean the layout has been saved.
The Home worker prepares a bounded streaming splice, validates Android/X4/X3
geometry and publishes through F33's atomic LayoutStore/FilePublish path. Paint
never parses, reads storage or writes. Add preserves unknown fields, instances,
settings and future-class overrides. Remove deletes the selected placement and
retains orphan override bytes; generated IDs avoid both live and orphan IDs.
Reset is explicit and restores the owned default with a monotonically increasing
revision. It never changes books, reader state, pairing or sync journals.

## Presentation approval

Audited BookSync `origin/feature/0.12` design at `0c4b869f`:

- `docs/design/booksync-home/DESIGN.md` §3.5 (lines 326–346) approves X4
  touch/button editor operations and requires an X3 Settings-list equivalent.
- Revision-16 `mockups.html` has `x4pro-edit`, `x4c-edit`, `x4c-edit-options`
  and `x4c-edit-carry`; the prototype's `editHead`, `pickerView`, `tilemenu`
  and `editReset` interactions define the add/remove/reset subset.
- Firmware `SCREENS.md` approves B1–B5 and bottom-docked touch keyboards;
  those screens do not add an X3 Home editor presentation.
- No X3 editor scene existed. BookSync [PR #213](https://github.com/Fledgewing/Orbify/pull/213)
  adds the missing Settings-list mockups, explicitly **NEEDS APPROVAL**.
  Merging that proposal does not approve implementation.

X4 Pro uses header/tile taps; Classic uses Previous/Next and Select with Back.
The logical Right/More action opens editing. Add offers installed starter widgets
only. Selecting a tile exposes Remove and Done. Reset focuses Keep first. Back
from pending work closes presentation without interrupting atomic publication.
No keyboard is needed. Move/resize and page operations remain F35b/F35c.
`CROSSINK_APP_CAP_HOME_EDITOR` excludes the editor presentation from C3/X3 images;
the shared service is tested there. X3 editor UI: **NEEDS APPROVAL**.

## Resource bounds and verification

The editor has a fixed workspace (compile-time cap 3 KiB) inside the single
fallible Home-worker allocation, capped at 28 KiB. It is reused and released
before reader entry; a task stack or second framebuffer cannot hold this payload.
There is no per-edit JSON tree or payload heap allocation. Source readers close
before same-path validation and before publication renames. A source reader and
staging writer may coexist on different paths.

`test/host/layout_editor` covers atomic publication cuts, read-only/full storage,
stale revision/index, first/middle/last/empty removal, identity collisions, missing
override groups, class capacity, unknown bytes, reset cancellation and retired
presentation. `test/simulator/editor.py` runs once in all three profiles, captures
Pro touch/Classic button scenes and X3 unchanged Home, and verifies add/remove/
reset/restart/stale/Keep using real synthetic HAL storage. A failed scenario is
investigated, never retried unchanged. Native host heap and stack values cannot
stand in for hardware internal heap/largest block or FreeRTOS high-water marks.

Maintainer hardware verification, after sideloading the test image: on Pro tap
Edit, Add Browse, select/remove a tile, cancel Reset, then confirm Reset. On
Classic use Right/More, Previous/Next, Select and Back for the same sequence.
Reboot after each saved edit: expect a complete prior or new layout, valid focus,
and unchanged reading position/stats. Test a full/read-only synthetic card:
expect an error and a recoverable complete layout. On X3, confirm no editor
entry appears and normal Home/open/Back still works. No EPUB cache reset is
needed. Inspect internal heap/largest block and task stack high-water marks;
S3 PSRAM is separate. These device checks remain maintainer-only and pending.
